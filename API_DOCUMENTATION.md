# IAM eSign Broker API Reference

This is a framework- and language-neutral reference for integrating an application with the Nagaland IAM eSign broker. It describes only the work required in the consuming application.

## Integration model

```text
Your backend  -- create request -->  IAM eSign broker
Browser       <-- handoff URL ------  IAM eSign broker
Browser       -- redirect -------->  IAM handoff URL
Browser       <-- completion URL --  IAM eSign broker
Your backend  -- status/download --> IAM eSign broker
```

The API key is used only between your backend and IAM. The browser must never receive it.

## What your application must implement

1. A server-side endpoint that uploads the document to IAM's create endpoint.
2. A secure server-side store for the eSign API key, transaction ID, business reference, and random `state` value.
3. A browser redirect to the `handoff_url` returned by IAM.
4. The configured `completion_url` endpoint, which validates the returned transaction ID and `state`.
5. Server-side calls to obtain the final status and download the completed file.

## Prerequisites

Before integration, provide the public `completion_url` for your application to the Department of IT&C. The Department of IT&C will provide the eSign API key.

Store the API key only in your server-side secret manager. The `completion_url` sent when creating a request must exactly match the URL you provided.

## IAM base URL

Set `IAM_BASE_URL` to the IAM installation URL without a trailing slash.

Example:

```text
https://iam.example.gov.in
```

All endpoint paths in this guide are relative to this base URL.

## Authentication

Every API request needs these headers:

```http
X-IAM-eSign-Key: <eSign-api-key>
Accept: application/json
```

| Operation | Method and path | Required client scope |
| --- | --- | --- |
| Create signing request | `POST /api/esign/requests` | `esign.request` |
| Get transaction status | `GET /api/esign/requests/{transaction_id}` | `esign.read` |
| Get eSign artifacts | `GET /api/esign/requests/{transaction_id}/artifacts` | `esign.read` |
| Download signed document | `GET /api/esign/requests/{transaction_id}/download` | `esign.read` |

`transaction_id` is generated by IAM. Treat it as an opaque identifier.

## Create a signing request

Create a request from your backend with `multipart/form-data`.

```bash
curl --request POST "$IAM_BASE_URL/api/esign/requests" \
  --header "X-IAM-eSign-Key: $IAM_ESIGN_API_KEY" \
  --header "Accept: application/json" \
  --form "document=@/secure/uploads/approval.pdf;type=application/pdf" \
  --form "client_reference=approval-12345" \
  --form "completion_url=https://client.example.gov.in/esign/complete" \
  --form "state=$ESIGN_STATE" \
  --form "mode=visible" \
  --form "signer_name=Jane Doe" \
  --form "signature_position=bottom-right"
```

### Request fields

| Field | Required | Rules |
| --- | --- | --- |
| `document` | Yes | PDF, JPG, JPEG, or PNG; maximum 20 MB. |
| `client_reference` | Yes | Application-owned ASCII alpha-dash identifier, maximum 160 characters. It should uniquely identify the business record or signing attempt. |
| `completion_url` | Yes | Exact value configured in the OAuth client's **eSign Completion URL** field; maximum 2,000 characters. |
| `state` | No, strongly recommended | Opaque value returned to the completion URL; maximum 255 characters. Generate it with a cryptographically secure random generator. |
| `mode` | No | `direct` (default) or `visible`. Use `direct` for every request in a document that requires multiple signatures. |
| `signature_field_name` | No | Field name for a direct signature; maximum 120 characters. |
| `signer_name` | Required for `visible` mode | Name used for visible signing; maximum 120 characters. |
| `signature_position` | No | Visible-signature placement: `top-left`, `top-right`, `bottom-left`, or `bottom-right`. Omit it to use IAM's default bottom-right placement. Ignored by direct mode. |
| `uid_token` | No | UID token obtained from a previous completed transaction for the same signer; maximum 72 characters. Send it only from your backend. |

### Multiple signatures and signing modes

For a document that will receive more than one signature, use `mode=direct` for **every** signing request. `direct` creates an append-only, invisible signature field and preserves the existing PDF bytes and signatures, so the completed PDF can be submitted again for the next signer.

`visible` mode prepares a new, rendered PDF in order to add visible signer information. It does not preserve prior PDF signatures and therefore must not be used for a multi-signature sequence. Use `visible` only when one visible signature is required and the document does not need to retain an earlier PDF signature.

For visible mode, optionally send `signature_position` to select one of the four page corners. If the field is omitted, IAM uses the bottom-right position.

### Successful response

A new request returns `201 Created`:

```json
{
  "transaction_id": "5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e",
  "client_reference": "approval-12345",
  "status": "awaiting_signer",
  "handoff_url": "https://iam.example.gov.in/esign/handoff/<single-use-token>"
}
```

Persist the following against the browser session and your business record before redirecting:

- `transaction_id`
- the generated `state`
- original document filename or other download metadata

Then redirect the browser to the returned `handoff_url`. It is single-use and expires after 10 minutes. Do not request this URL from your backend: visiting it begins the browser signing journey.

### Idempotency

`client_reference` is idempotent for an OAuth client. Repeating the same reference returns the original transaction instead of creating another one. This response has no new `handoff_url`.

Use a durable unique business reference and persist the first transaction result before redirecting. Start a truly new signing attempt with a new reference.

## Handle the completion redirect

IAM redirects the browser to `completion_url` after processing C-DAC's response:

```text
https://client.example.gov.in/esign/complete?
  esign_transaction_id=5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e&
  state=<original-state>
```

At this endpoint, your application must:

1. Read `esign_transaction_id` and `state`.
2. Look up the transaction in the current browser's server-side session or another protected store.
3. Reject the request if the transaction is absent or state does not match. Use a constant-time comparison when available.
4. Call the status endpoint below to obtain the authoritative result.

Do not mark a business record as signed merely because the browser reached the completion URL.

## Get transaction status

```bash
curl --request GET \
  --header "X-IAM-eSign-Key: $IAM_ESIGN_API_KEY" \
  --header "Accept: application/json" \
  "$IAM_BASE_URL/api/esign/requests/5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e"
```

Example completed response:

```json
{
  "transaction_id": "5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e",
  "client_reference": "approval-12345",
  "status": "completed",
  "signer_name": "A. Example"
}
```

When signing fails, the payload can include `failure_reason`:

```json
{
  "transaction_id": "5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e",
  "client_reference": "approval-12345",
  "status": "failed",
  "failure_reason": "The eSign response could not be validated."
}
```

| Status | Meaning |
| --- | --- |
| `awaiting_signer` | Transaction exists but the browser has not used the handoff URL. |
| `awaiting_response` | Browser entered the C-DAC signing journey; IAM is waiting for the response. |
| `completed` | IAM validated the response and the signed document is ready. |
| `failed` | Signing did not complete; inspect `failure_reason` where present. |

Treat unknown statuses as not completed.

## Get eSign artifacts and reuse a UID token

After the status is `completed`, retrieve the XML artifacts and UID token from your backend:

```bash
curl --request GET \
  --header "X-IAM-eSign-Key: $IAM_ESIGN_API_KEY" \
  --header "Accept: application/json" \
  "$IAM_BASE_URL/api/esign/requests/5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e/artifacts"
```

```json
{
  "transaction_id": "5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e",
  "status": "completed",
  "esign_xml": "<Esign ...>",
  "esign_response_xml": "<EsignResp ...>",
  "uid_token": "..."
}
```

Store these values securely. For a later signing request by the same signer, send the stored `uid_token` as the `uid_token` multipart field. Do not place XML or UID tokens in a browser session, browser redirect, URL, or client-side JavaScript.

## Download a signed document

Call this only after a fresh status response says `completed`.

```bash
curl --request GET \
  --header "X-IAM-eSign-Key: $IAM_ESIGN_API_KEY" \
  --output signed-approval.pdf \
  "$IAM_BASE_URL/api/esign/requests/5c8e9b5e-33ee-4d79-9aa4-84d0bb08dd0e/download"
```

The response body contains the signed document bytes. Stream the result through your backend with a safe attachment filename and an appropriate content type.

Never expose an unauthenticated download route that accepts arbitrary transaction IDs. Verify that the current browser session owns the transaction before allowing the download.

## Errors

| HTTP status | Meaning | Recommended handling |
| --- | --- | --- |
| `401` | API key is missing, invalid, or revoked. | Check the server-side secret or issue a replacement key in IAM Admin. |
| `403` | Client lacks the required eSign scope or does not own the transaction. | Enable the scope or use the correct client's API key. |
| `409` | Document is not ready, or the handoff is in an invalid state. | Check status later, or create a new request when the handoff cannot be reused. |
| `410` | Handoff URL has expired or was already used. | Create a new request with a new client reference. |
| `422` | Invalid request field, upload, mode, or completion URL mismatch. | Validate the input and ensure the configured completion URL exactly matches. |

IAM responses may include a JSON `message` field. Log upstream details securely, but present safe user-facing messages.

## Security requirements

- Keep the API key, uploaded document, state, XML artifacts, UID token, and IAM responses server-side.
- Use HTTPS in production for both the application and IAM.
- Bind every transaction ID and state value to the initiating browser session.
- Use cryptographically random state values and constant-time state comparison.
- Check fresh IAM status before granting download access or marking a record as signed.
- Store application-specific transaction metadata in a durable database; browser sessions alone are insufficient for audit and recovery.
- Do not log API keys, C-DAC request XML, or signed document content.
